# План 01. v0: сквозной срез

## Overview

Первая контрольная точка v0 из `docs/development-plan.md`: цепочка локальное описание задачи → снимок диффа → ручная свежая сессия → импорт → понятный отчёт. На ней начинаются наблюдения пилота; готовым v0 срез не считается.

```
plait run new <slug>
plait ctx save [KEY] < task.md        # задача и критерии, пробелы явно
plait review export                   # снимок + пакет для свежей сессии
  … разработчик открывает новую сессию агента, отдаёт ей пакет, получает JSON …
plait review import <file|->          # проверка схемы и привязки к снимку
plait review report                   # отчёт с меткой покрытия
plait next --json                     # что делать дальше на любом шаге
```

Входит: каркас с make-целями, контракт вывода, слои конфига, run и `state.json`, `next`, `ctx save`, снимок в `refs/plait`, экспорт пакета, импорт, отчёт.

Не входит (остаток v0, план 02+): `setup`/`init`, `doctor` и закрытый контур, `ctx <KEY>` через агента, сравнение прогонов и статусы находок, захват результатов проверок, `mr describe`, аудит-журнал, headless-запуск агентов.

## Solution Overview

**Снимок — git-коммит в `refs/plait/snapshots/<run>/<n>`.** Дерево рабочей копии, включая untracked и исключая игнорируемое и `.plait/`, пишется через временный `GIT_INDEX_FILE`, поэтому индекс разработчика не трогается. Git сам считает дифф между снимками — это понадобится для сравнения прогонов. Локальные ref'ы не пушатся по умолчанию.

**Свежая сессия вручную.** `review export` пишет самодостаточный пакет: агент в новой сессии получает критерии и код, а не рассуждения автора. Результат возвращается JSON по схеме `review-findings/v1` и импортируется с проверкой, что он относится к этому снимку.

**Схемы — один источник.** JSON Schema вшиты через `go:embed`; ими же валидируется импорт (`github.com/santhosh-tekuri/jsonschema/v6`) и их же агент получает в пакете.

**Состояние переживает прерывание.** Все записи в `.plait/` — атомарные (временный файл + `rename`); повтор команды после сбоя доводит шаг или ничего не меняет.

## Technical Details

Раскладка:

```
cmd/plait/main.go
internal/cli/       # cobra-команды, только разбор флагов и вызов пакетов
internal/output/    # TTY/JSON, конверт ответа, ошибки с exit code
internal/config/    # koanf: embed defaults → /etc/plait → ~/.config/plait → .plait/config.yaml → env PLAIT_* → флаги
internal/run/       # run, state.json, текущий run, next
internal/task/      # ctx save → task.md
internal/vcs/       # снимок через exec git
internal/review/    # пакет, импорт, отчёт; schemas/*.json и templates/*.tmpl через embed
```

- ➕ Конфиг: `PLAIT_REVIEW_BASE` → `review.base`, списки в env через запятую; `~/.config` уважает `XDG_CONFIG_HOME`. Каждый слой декодируется отдельно до слияния, чтобы ошибка типа называла свой файл.

Контракт вывода:

- JSON, если stdout не TTY (`golang.org/x/term`) или указан `--json`; иначе человекочитаемый текст.
- Успех: `{"ok": true, "data": {...}}`. Ошибка: `{"ok": false, "error": {"code": "...", "message": "...", "fix": "..."}}`, где `fix` — что сделать и какую команду вызвать.
- Exit codes: 0 — ок, 2 — невалидный артефакт или ввод, 3 — запрещено политикой, 4 — нужен человек, 1 — внутренняя ошибка.
- В JSON-режиме конверт ошибки идёт в stdout, чтобы агент читал один поток; в текстовом — `error:`/`fix:` в stderr. Ошибка разбора аргументов cobra — `usage` (exit 2) с `fix: <команда> --help`.
- ➕ testscript-команда `exitcode N cmd args...` проверяет точный exit code: встроенный `exec` различает только ноль и не ноль.

Run:

- `.plait/runs/<id>/`, `id` = `YYYY-MM-DD-<slug>` или `<KEY>-<slug>`. Текущий run — `.plait/current` (имя run).
- ➕ `run new <slug> [--key KEY]`. Корень — ближайший предок с `.git`, вне репо — рабочий каталог. Битый `state.json` — `NeedsHuman` (exit 4): чинить чужой артефакт агенту нельзя.
- `state.json`: `schema` (`plait-state/v1`), `id`, `created_at`, `task` (`source`, `has_criteria`), `snapshots` (`n`, `commit`, `tree`, `base`, `head`, `created_at`), `reviews` (`n`, `snapshot`, `imported_at`, `coverage`), `step` ∈ `new | task_saved | exported | imported | reported`.
- `next` по `step` отдаёт `run`, `step`, `do`, `inputs`, `output` (`cmd`, `schema`), `allowed`.
- ➕ `next` — чистая функция от `state.json`, пути в `inputs` от корня репо; ответ ревью лежит в `.plait/runs/<id>/review-<n>.json`. Неизвестный `step` или `exported`/`imported` без снимка/ревью — `NeedsHuman` (exit 4).

`ctx save`:

- Вход — Markdown со stdin или `--file`; `--source` (`local`, `jira`, `agent`), по умолчанию `local`.
- Нормализация в `task.md`: заголовок, описание, раздел «Критерии приёмки». Если критериев нет — раздел содержит явную метку `<!-- plait:gap acceptance_criteria -->` и текст «не заданы»; `has_criteria=false`. Нормализация критерии не придумывает.
- ➕ Заголовок — первый `#`, иначе первая строка; `KEY` становится префиксом заголовка и `task.key` в `state.json`, источник — меткой `<!-- plait:source … -->`. Критерии — раздел «Критерии приёмки»/«Acceptance criteria» любого уровня; нормализация `task.md` повторно его не меняет. Изменённая задача возвращает run в `task_saved`: прежние снимки устарели. Stdin-терминал без `--file` — `Invalid`, а не ожидание ввода.

Снимок:

- База: `merge-base HEAD <base>`, `<base>` из конфига `review.base` (по умолчанию `origin/HEAD`, затем `main`, затем `master`); если не найдена — exit 2 с `fix` про `--base`.
- `GIT_INDEX_FILE=<tmp> git read-tree HEAD` → `git add -A -- . ':(exclude).plait'` → `git write-tree` → `git commit-tree -p HEAD` → `git update-ref refs/plait/snapshots/<run>/<n>`.
- Пустой дифф относительно базы — exit 2 «нечего ревьюить».
- «Рабочая копия изменилась после снимка» = дерево, посчитанное тем же способом, ≠ `tree` снимка.
- ➕ Коммит снимка детерминирован: автор и коммитер `plait`, дата коммита HEAD, `--no-gpg-sign`. Тот же tree на том же HEAD даёт тот же коммит, и пользовательский `user.email` не нужен. Нет коммита в HEAD или нет репо — `Invalid` `no_head`; база без общего предка — `no_merge_base`.

Пакет `review export` → `.plait/runs/<id>/review-<n>/`:

- `package.md`: роль ревьюера и правила ответа, `task.md`, правила репо (файлы из `review.rules`, по умолчанию `AGENTS.md`, `CLAUDE.md`, `.plait/rules.md` — какие есть), дифф `base..snapshot`, метка покрытия, id снимка, схема ответа.
- Метка покрытия: `criteria`, если `has_criteria`, иначе `diff_only`.
- Повторный `export` без изменений рабочей копии отдаёт тот же снимок и пакет.
- ➕ Записанный `review-<n>/package.md` не меняется: снимок переиспользуется, только если коммит, база и отрендеренный пакет совпадают байт в байт; иначе `n+1`, даже при том же коммите (новая задача или правила). `vcs.Snapshot` только считает коммит, ref ставит `SetRef` после выбора `n`. Пути `review.rules` — только внутри репо (`os.Root`), иначе `Invalid`; `--base` — слой флагов конфига.

`review-findings/v1`: `snapshot` (commit), `coverage`, `findings[]` с `id`, `severity` (`blocker | major | minor | nit`), `file`, `line`, `title`, `rationale`, необязательный `criterion`.

`review import`:

- Валидация по схеме — иначе exit 2 с путём до поля в `fix`.
- `snapshot` ≠ последнему снимку run — exit 2. Рабочая копия изменилась после снимка — импорт проходит, отчёт помечается `stale`.
- Повторный импорт того же файла — без изменений, exit 0.
- ➕ `coverage` ответа ≠ метке пакета — `Invalid`; повтор `id` находки — `schema_violation`. Другой ответ на снимок, у которого ревью уже импортировано, — `NeedsHuman` `review_exists`: какой ответ оставить, решает человек. Ответ пишется до `state.json`, поэтому повтор после сбоя доводит импорт. Пустой stdin — `no_answer_input`.
- ➕ testscript-команды `capture VAR REGEXP` (группа из последнего stdout в env) и `expand SRC DST` (файл с подстановкой `$VAR`) подставляют коммит снимка в фикстуру ответа.

`review report`: Markdown (TTY) или JSON — метка покрытия словами («проверено по критериям задачи» / «проверен только дифф»), снимок, `stale`, находки по серьёзности.
- ➕ Отчёт строится по последнему импортированному ревью, `stale` — дерево рабочей копии против дерева его снимка. Метки по-английски, как весь вывод CLI: `coverage_label` в JSON. Шаг `imported` → `reported`, другие шаги отчёт не меняет. Пропавший `review-<n>.json` — `Invalid` `review_missing` (повторный импорт чинит), испорченный или чужой — `NeedsHuman` `review_corrupt`.
